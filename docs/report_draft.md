## 0. 요약

본 과제는 영업배전 자료 추출 업무에 대규모언어모델(LLM) 기반 Text2SQL 기술의 업무 도입 가능성을 검증하는 것을 목적으로 한다. 한전 공개 데이터로 시험용 DB를 구축하고, 자연어 질문을 SQL로 자동 변환하는 파이프라인을 구현하여 정확도·안정성·보안성을 종합 점검하였다.

**핵심 성과**

| 항목 | 내용 |
|------|------|
| 정확도 (EX) | gpt-oss-120b 기준 **100%** (11/11 시나리오) |
| 시맨틱레이어 효과 | 적용 전 54.5% → 적용 후 100% (**+45.5%p**) |
| 채택 모델 | gpt-oss-120b (정확도·실행 성공률 모두 우위) |
| 구축 DB | PostgreSQL 12개 테이블 (한전 OPEN API 기반) |
| 현장 활용 수준 | 정확도 기준(EX ≥ 70%) **달성** |

자연어 질문을 SQL로 자동 변환하는 6단계 파이프라인을 구축하였으며, 도메인 특화 시맨틱레이어 적용이 정확도에 결정적 영향을 미침을 확인하였다. 광주·전남 사업소 시범 도입을 시작으로 단계적 확대를 추진할 계획이다.

## I. 연구 과제 개요

### 1. 추진 배경 및 문제 정의

영업배전 자료 추출 업무는 현재 한전KDN 위탁운영에 의존하고 있으며, 2025년 기준 연간 13,582건의 자료추출 요청이 발생하였다. 자료 요청부터 결과 수령까지 다수의 담당자가 개입하는 복잡한 승인·처리 과정으로 인해 신속한 의사결정이 저해되고 있다.

**현재 업무 흐름 (4단계 수동 처리)**

```
사업소 직원          업무 담당자         KDN 시스템 담당자      사업소 직원
(자료 요청)    →    (요청 승인)     →    (자료 추출)      →   (결과 확인)
```

> 요청 예시: '24~'25년 아파트 고객번호 단위 월별 전력사용량 추출 요청

**개선 방향 (AI 자동 처리)**

```
사업소 직원          AI Agent              업무 DBMS           사업소 직원
(자연어 질문)   →   (쿼리 자동 생성)  →   (쿼리 실행)    →   (결과 확인)
```

자연어로 질문하면 AI 시스템이 데이터 조회 명령어(SQL)를 자동 생성하여 사업소 직원이 직접 데이터를 조회할 수 있는 구조로 전환한다.

## II. 연구 개발 내용

### 1. 기술 검토

#### Text2SQL 기술 개요

Text2SQL은 자연어 질문을 데이터베이스 조회 명령어(SQL)로 자동 변환하는 기술이다. 최근 LLM(대규모언어모델)의 발전으로 복잡한 규칙 기반 접근 없이도 높은 변환 정확도를 달성할 수 있게 되었다.

#### 주요 기술 요소

| 기술 | 역할 | 적용 내용 |
|------|------|---------|
| LLM (Large Language Model) | 자연어 → SQL 변환 | GPT-oss-120b, GPT-4o, Qwen3-32b 3종 비교 평가 |
| RAG (Retrieval-Augmented Generation) | 도메인 지식 주입 | 시맨틱레이어: 테이블 정의·집계규칙·조인관계 프롬프트 삽입 |
| 시맨틱레이어 | 도메인 규칙 명세 | 단위, 집계 방식, 코드 체계 등 한전 DB 특화 규칙 정의 |

#### 국내외 유사 사례

Text2SQL 기술은 BIRD, Spider 등 학술 벤치마크를 중심으로 빠르게 발전하고 있으며, 금융·제조 분야의 기업 DB 적용 사례가 증가하고 있다. 공통적으로 도메인 특화 프롬프트 설계(시맨틱레이어)가 범용 LLM 성능을 결정적으로 향상시키는 핵심 요소로 확인된다.

#### 처리 흐름

자연어 질문이 입력되면 다음 6단계를 순차적으로 거쳐 결과를 반환한다.

| 단계 | 구성요소 | 역할 |
|------|---------|------|
| 1 | 코드 변환기 | 질문의 지역명·업종명을 DB 코드 서브쿼리로 변환 |
| 2 | 스키마 문서 조합기 | DB 구조 + 집계 규칙 + 조인 관계를 LLM 프롬프트로 조합 |
| 3 | SQL 생성기 | LLM API 호출로 SQL 생성 |
| 4 | 안전성 검사기 | 쓰기 구문 및 위험 키워드 차단 |
| 5 | SQL 실행기 | 읽기 전용 DB 실행 (5초 타임아웃) |
| 6 | 결과 반환 | 행·컬럼 구조화 반환 |

**처리 예시**

```
입력: "2024년 제조업 전력사용량이 가장 많은 광역시도는?"

[코드 변환기]
제조업 → biz_code = (SELECT code FROM common_code WHERE code_name='제조업')

[SQL 생성기 출력]
SELECT m.code_name AS 광역시도, SUM(i.power_usage) AS 전력사용량
FROM industry_type i
JOIN common_code m ON m.code_type='metroCd' AND m.code=i.metro_code
WHERE i.year='2024'
  AND i.biz_code = (SELECT code FROM common_code WHERE code_type='bizCd' AND code_name='제조업')
GROUP BY i.metro_code
ORDER BY 전력사용량 DESC
LIMIT 1

[실행 결과]
광역시도: 경기도 / 전력사용량: 38,291,023 MWh
```

### 3. 데이터 수집 및 전처리

#### 데이터 수집

실제 운영 DB(Oracle Exadata) 접근 전 검증 단계로, 한전 공개 데이터를 수집하여 시험용 PostgreSQL DB를 구축하였다. 한전 OPEN API와 data.go.kr 파일데이터 두 경로로 데이터를 수집하였으며, 이번 검증에는 사용 빈도가 높은 한전 OPEN API 기반 핵심 12개 테이블을 PostgreSQL에 적재하여 사용하였다.

| 수집 경로 | 수집 방법 | 비고 |
|-----------|----------|------|
| 한전 OPEN API (bigdata.kepco.co.kr) | API 호출 자동화 | 검증 DB 적재 (12개 테이블, 2022~2026년) |
| data.go.kr 파일데이터 | 크롤링 + CSV 적재 | 추가 수집 (시간별 수요·PPA·상계거래 등, 차기 확장 대상) |

**검증 DB 구성 (PostgreSQL, 12개 테이블)**

| 분류 | 주요 데이터 |
|------|-----------|
| 전력사용 | 계약종별·산업분류별 전력사용, 가구당 평균 사용량 |
| 고객·청구 | 청구서 발송 유형, 복지할인, 산업별 고객 증감 |
| 설비·기타 | EV 충전, 신재생에너지, 분산전원, 전자입찰계약, 공통코드 |

#### 전처리

데이터 품질 점검 후 다음 항목을 정비하였다.

- **지역 코드 통일**: 지역명 텍스트(서울특별시, 전라북도 등)를 숫자 코드로 변환, `common_code` 테이블과 연계
- **집계행 제거**: API 원본 데이터의 전국 합계행(`totData`) 제거하여 이중 집계 방지
- **빈값 처리**: 빈 문자열(`""`)을 `NULL`로 변환
- **업종 코드 정비**: 한국표준산업분류(KSIC) 11차 기준으로 코드명 현행화
- **지역명 현행화**: 강원특별자치도, 전북특별자치도 반영

### 4. 핵심 기능 구현

#### 코드 변환기 (normalizer)

한전 DB는 지역과 업종을 숫자 코드로 저장한다. 코드 변환기는 자연어 질문에서 지역명·업종명을 감지하여 `common_code` 테이블 서브쿼리 힌트를 자동 생성한다. 이를 통해 LLM이 코드를 하드코딩하는 오류(`biz_code = 'C'`)를 방지하고, 코드 체계가 변경되어도 자동으로 대응한다.

#### 스키마 문서 조합기 (semantic_builder)

LLM이 올바른 SQL을 생성하려면 테이블 구조 외에 도메인 규칙을 알아야 한다. 스키마 문서 조합기는 3개 레이어를 조합하여 LLM 프롬프트를 구성한다.

| 레이어 | 내용 | 예시 |
|--------|------|------|
| 메타데이터 레이어 | 테이블 정의(DDL), 컬럼 예시값 | `gen_source` 예시: 태양광, 풍력, 소수력 |
| 의미규칙 레이어 | 단위, 집계 규칙, 사용 금지 패턴 | `area_capacity`는 MAX 사용 (SUM 시 중복 집계) |
| 조인관계 레이어 | 테이블 간 JOIN 가능 컬럼 정의 | `city_code`는 반드시 `metro_code`와 함께 사용 |

#### 안전성 검사기 (safety)

LLM 생성 SQL 실행 전 4단계 검사를 수행한다.

1. **주석 제거**: 주석 내 금지 키워드 은닉 차단
2. **첫 토큰 검사**: `SELECT`/`WITH`/`EXPLAIN` 외 차단
3. **금지 키워드 검사**: `INSERT`, `UPDATE`, `DELETE`, `DROP` 등 차단
4. **테이블명 검사**: 스키마에 없는 테이블 참조 차단

`executor`의 PostgreSQL 읽기 전용 세션과 함께 이중 방어 구조를 형성한다.

#### SQL 실행기 (executor)

- PostgreSQL 읽기 전용 세션(`SET SESSION readonly`)으로만 DB 연결
- 결과 행 최대 100개 자동 제한
- 별도 스레드에서 실행, 5초 초과 시 타임아웃 강제 종료

### 5. 검증

#### 평가 방법

| 지표 | 정의 | 측정 방법 |
|------|------|----------|
| **정확도 (EX)** | 생성 SQL 실행 결과가 정답(gold)과 일치하는 비율 | gold SQL과 gen SQL 실행 결과 비교 |
| **실행 성공률** | SQL 문법 오류·타임아웃 없이 실행 완료되는 비율 | 실행 오류·타임아웃 발생 여부 집계 |
| **거절 정확도** | 조회 불가 질문을 올바르게 거절하는 비율 | IMPOSSIBLE 시나리오 거절 여부 판정 |

정확도 판정은 완전 일치 외에 두 가지 유연한 기준을 추가 적용하였다.
- **superset match**: 생성 SQL이 정답 수치에 추가 컬럼을 포함한 경우 정답 인정
- **subset match**: 생성 SQL이 정답 핵심 수치만 반환하고 정답이 중간 계산값을 추가 포함한 경우 정답 인정

#### 테스트 시나리오 구성

현장 업무에서 실제로 발생할 수 있는 질문 유형을 난이도별로 11개 시나리오로 구성하였다.

| 유형 | 시나리오 수 | 예시 질문 |
|------|-----------|---------|
| 단일 테이블 단순 조회 | 4개 | "2024년 제조업 전력사용량이 가장 많은 광역시도는?" |
| 단일 테이블 복합 집계 | 3개 | "산업용 계약의 계약전력 대비 사용량 비율은?" |
| 멀티 테이블 JOIN | 2개 | "제조업 전력사용량 증감과 신규 계약 건수 상관관계" |
| 조회 불가 판정 | 1개 | 스키마에 없는 정보 요청 → 거절 |
| 복합 CTE | 1개 | 다단계 집계 및 순위 산출 |

### 2. 개선 및 업무 적용 계획

#### 개선 계획

**대화형 질의 고도화**

현재 파이프라인은 질문 1건에 SQL 1건을 생성하는 단일 턴 방식이다. 다음 단계로 멀티턴 방식을 도입하여 앞선 질문의 결과를 이어받아 추가 질의를 할 수 있도록 고도화한다.

```
예시)
1문: "2024년 제조업 전력사용량 상위 5개 시도는?"
     → [결과: 경기, 충남, 전남, 경북, 경남]
2문: "그 중 전년 대비 증가한 곳은?"  ← 앞 결과를 이어받아 조회
```

**개인·부서 맞춤 지식 연계**

현재는 공통 DB 조회만 가능하다. 부서별 업무 문서, 과거 보고서, 담당자별 자주 쓰는 질의 패턴을 RAG(검색 증강 생성) 기술로 연계하여, 같은 질문이라도 부서 맥락에 맞는 답변을 제공할 수 있도록 한다.
