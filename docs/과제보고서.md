# I. 연구 과제 개요

## 1. 추진 배경 및 문제 정의

### 1.1 추진 배경

영업배전 자료 추출 업무는 현재 한전KDN 위탁운영에 의존하고 있으며, 2025년 기준 연간 **13,582건**의 자료추출 요청이 발생하였다. 자료 요청부터 결과 수령까지 다수의 담당자가 개입하는 복잡한 승인·처리 과정으로 인해 반복적인 위탁 비용이 발생하고, 신속한 의사결정이 저해되고 있다.

**현재 업무 흐름 (4단계 수동 처리)**

```
사업소 직원        업무 담당자        KDN 시스템 담당자       사업소 직원
(자료 요청)   →   (요청 승인)    →    (자료 추출)      →    (결과 확인)
```

> 요청 예시: '24~'25년 아파트 고객번호 단위 월별 전력사용량 추출 요청

반복 유형의 단순 조회임에도 매 건마다 요청서 작성·승인·위탁 처리를 거치므로, 처리에 수일이 소요되고 담당자 업무 부담이 가중된다.

### 1.2 문제 정의

| 문제       | 내용                                     |
| -------- | -------------------------------------- |
| 위탁 의존    | 자료추출을 한전KDN에 위탁하여 반복 비용 발생 (연 13,582건) |
| 처리 지연    | 요청→승인→추출→확인 다단계 처리로 결과 수령까지 수일 소요      |
| 의사결정 저해  | 필요 시점에 데이터를 즉시 확보할 수 없어 정책 수립 지연       |
| 활용 역량 한계 | 직원이 직접 데이터를 조회할 수단이 없어 역량이 축적되지 못함     |
|          |                                        |

위 문제는 개별 담당자의 노력으로 해소하기 어려운 구조적 비효율이며, 자료 추출 권한과 지식이 위탁·소수 담당자에게 집중되어 조직 자산으로 확산되지 못한다는 한계를 동반한다.

## 2. 기술 개발 목표 및 기대효과

### 2.1 기술 개발 목표

대규모언어모델(LLM) 기반 자연어 데이터 탐색(Text-to-SQL 또는 NL2SQL, 이하 Text2SQL) 시스템을 구현하여, 사업소 직원이 자연어로 질문하면 AI가 데이터 조회 명령어(SQL)를 자동 생성·실행하는 구조의 **업무 도입 가능성을 검증**한다.

**개선 방향 (AI 자동 처리)**

```
사업소 직원        AI Agent             업무 DBMS          사업소 직원
(자연어 질문)  →  (쿼리 자동 생성)  →   (쿼리 실행)    →   (결과 확인)
```

| 목표 | 세부 내용 |
|------|-----------|
| SQL 자동 생성 | 자연어 질문 입력 시 DB 조회 SQL을 즉시 생성 |
| 정확도 검증 | 현장 활용 가능 수준(EX ≥ 70%) 달성 여부 정량 측정 |
| 안정성 확보 | 잘못된 SQL·위험 구문 차단, 읽기 전용 실행 |
| 보안성 점검 | 사내 폐쇄망 자체 호스팅 가능성(오픈웨이트 모델) 검토 |

※ **핵심 원칙**: AI는 자료 추출을 보조하는 도구이며, 생성된 SQL과 결과는 담당자가 확인한다. 실행은 읽기 전용으로만 수행되어 데이터 변경이 원천 차단된다.

### 2.2 기대효과

**위탁 비용 및 처리 시간 절감** — 연 13,582건('25년)의 위탁 자료추출을 직원이 직접 처리할 수 있어 한전KDN 위탁 비용과 수일간의 대기 시간이 절감된다.

**신속한 의사결정 지원** — 자연어 질문만으로 즉시 결과를 확보할 수 있어 요청·승인·처리 다단계를 생략하고 필요 시점에 데이터를 활용할 수 있다.

**데이터 활용 역량 확산** — 위탁·소수 담당자에게 집중된 자료 추출 역량이 일선 직원으로 확산되어 조직 전반의 데이터 기반 의사결정 문화를 정착시킨다.

**확장성 확보** — 시맨틱레이어 기반의 일관된 SQL 생성 구조로 조회 품질이 표준화되며, 타 시스템 및 데이터 시각화 서비스 연계를 위한 기반이 마련된다.

# II. 연구 개발 내용

## 1. 대상 기술 개요

### 1.1 Text2SQL 개요

Text2SQL은 자연어 질문을 데이터베이스 조회 명령어(SQL)로 자동 변환하는 기술이다. SQL 작성 능력 없이도 자연어만으로 데이터베이스에 질의할 수 있게 하여, 데이터 활용의 진입 장벽을 낮추는 것을 목표로 한다.

```
자연어 질문 → [스키마·규칙 주입] → [LLM SQL 생성] → [안전성 검사] → [실행] → 결과
```

(핵심 기능) 실제 데이터에 적용할 때 정확도를 좌우하는 요소는 LLM의 언어 능력 자체보다 다음 세 가지다.

- **스키마 연결(Schema Linking)**: 질문에 등장한 표현이 어느 테이블·컬럼에 해당하는지 정확히 연결하는 문제. 동의어·약어가 많을수록 어려워진다.
- **도메인 지식**: 코드 체계, 단위, 집계 규칙은 데이터베이스 외부에 존재하는 암묵지로, LLM이 스키마만으로는 알 수 없다.
- **질문의 모호성·불가 질의**: 데이터로 답할 수 없는 질문에 LLM이 그럴듯한 오답 SQL을 생성하는 위험.

이러한 어려움은 도메인 지식을 프롬프트에 주입하는 방식(in-context 지식 주입), 관련 예시를 동적으로 검색해 제공하는 방식(RAG), 생성 결과를 실행해 오류를 교정하는 방식(self-correction) 등 다양한 보완 기법이 함께 활용된다.

### 1.2 사용 모델
OpenRouter를 경유하여 여러 공급사의 모델을 동일한 인터페이스로 호출하고, 동일 조건에서 정확도를 비교하였다. 사내 폐쇄망 자체 호스팅을 전제로, 평가 대상을 모두 **오픈웨이트(가중치 공개)** 모델로 선정하였다.

| 모델               |   출시일   | 개발사      | 특징                     | 파라미터               |
| ---------------- | :-----: | -------- | ---------------------- | ------------------ |
| **gpt-oss-120b** | 2025.08 | OpenAI   | 채택 모델, 정확도·실행 성공률 최우수  | 117B (MoE, 활성 5B)  |
| DeepSeek V3.2    | 2025.12 | DeepSeek | 범용·추론 고성능, 256K 컨텍스트   | 685B (MoE, 활성 37B) |
| Qwen3-Coder-Next | 2026.02 | Alibaba  | 코딩·Text2SQL 특화, 효율적 추론 | 80B (MoE, 활성 3B)   |
※ MoE(Mixture of Experts): 전체 파라미터 중 입력마다 일부 전문가 네트워크만 활성화해 추론 비용을 낮추는 구조.
※ 평가 대상 3종은 모두 오픈웨이트 모델로, 외부 API 의존 없이 사내 폐쇄망에 자체 호스팅이 가능하여 자료 데이터의 외부 유출 없이 운영할 수 있다는 점에서 보안성 측면의 도입 적합성이 높다.

## 2. 시스템 구성도 및 처리 흐름

### 2.1 시스템 구성도

시스템은 사전 배치로 수행하는 **데이터 구축**과, 질문마다 실시간으로 수행하는 **질의 처리** 두 평면으로 구성된다.

```
【 데이터 구축 (배치) 】
  한전 OPEN API ──▶ 수집·적재 스크립트 ──▶ PostgreSQL
  (bigdata)          collect → build_db      12개 테이블
                     → migrate_to_pg

【 질의 처리 (실시간) 】
  자연어 질문
      │
      ▼
  ① 코드 변환기(normalizer)     지역·업종명 → common_code 서브쿼리 힌트
      │
      ▼
  ② 스키마 조합기(semantic_builder)  시맨틱레이어 3종 조합
      │     · 메타데이터 : DDL · 예시값
      │     · 의미 규칙  : 단위 · 집계 규칙
      │     · 조인 관계  : 복합키 · JOIN 규칙
      ▼
  ③ SQL 생성기(generator)       OpenRouter / gpt-oss-120b (temp=0) → SQL
      │
      ▼
  ③+ 자기검증(verify, 선택)      생성 SQL이 질문 조건을 반영했는지 점검·수정 · 조회 불가 시 거절
      │
      ▼
  ④ 안전성 검사기(safety)        SELECT·WITH만 허용 · 금지키워드 · 테이블 검증
      │
      ▼
  ⑤ SQL 실행기(executor)        PostgreSQL 읽기전용 · 5초 타임아웃 · LIMIT 100
      │
      ▼
  ⑥ 결과 반환                   행·컬럼 구조화 → 표 · 다운로드
```

| 모듈                         | 역할                                        |
| -------------------------- | ----------------------------------------- |
| 코드 변환기 (normalizer)        | 질문의 지역명·업종명을 DB 코드 서브쿼리로 변환               |
| 스키마 조합기 (semantic_builder) | DB 구조 + 집계 규칙 + 조인 관계를 LLM 프롬프트로 조합       |
| SQL 생성기 (generator)        | OpenRouter API 호출로 SQL 생성 (temperature=0) |
| 자기검증기 (verify, 선택)         | 생성 SQL의 질문 조건 반영 여부 점검·수정, 조회 불가 질문 거절    |
| 안전성 검사기 (safety)           | 쓰기 구문 및 위험 키워드 차단, 테이블명 검증                |
| SQL 실행기 (executor)         | 읽기 전용 DB 실행 (5초 타임아웃, 최대 100행)            |

### 2.2 처리 흐름

```
자연어 질문 입력
       ↓
코드 정규화 (지역·업종명 → common_code 서브쿼리 힌트)
       ↓
스키마 컨텍스트 조합 (시맨틱레이어 3종)
       ↓
LLM SQL 생성 (gpt-oss-120b, 스키마·규칙 기반)
       ↓
자기검증 (선택: 질문 조건 반영 점검·수정, 조회 불가 시 거절)
       ↓
안전성 검사 (SELECT/WITH 전용, 금지 키워드·테이블 검증)
       ↓
읽기 전용 실행 (PostgreSQL, 5초 타임아웃)
       ↓
결과 표시 (표 · CSV 다운로드)
```

#### 실제 처리 예시

**[입력] 자연어 질문**

> "2024년 제조업 전력사용량이 가장 많은 광역시도는?"

**[Step ①] 코드 정규화**

질문에서 업종명 '제조업'을 감지하여 코드 하드코딩(`biz_code = 'C'`) 대신 common_code 서브쿼리 힌트를 생성한다.

```
제조업 → biz_code = (SELECT code FROM common_code
                     WHERE code_type='bizCd' AND code_name='제조업')
```

**[Step ②~③] 스키마 조합 및 SQL 생성**

시맨틱레이어(테이블 정의·단위·조인 규칙)와 코드 힌트를 프롬프트에 주입하여 SQL을 생성한다.

```sql
SELECT m.code_name AS 광역시도, SUM(i.power_usage) AS 전력사용량
FROM industry_type i
JOIN common_code m ON m.code_type='metroCd' AND m.code=i.metro_code
WHERE i.year='2024'
  AND i.biz_code = (SELECT code FROM common_code
                    WHERE code_type='bizCd' AND code_name='제조업')
GROUP BY i.metro_code, m.code_name
ORDER BY 전력사용량 DESC
LIMIT 1
```

**[Step ④~⑤] 안전성 검사 및 실행**

`SELECT`로 시작·금지 키워드 없음·테이블명 검증 통과 → PostgreSQL 읽기 전용 세션에서 실행.

**[출력] 결과**

> 광역시도: 경기도 / 전력사용량: 68,684,716,267 kWh (약 68,685 GWh)

| 공통 코드       | 지역·계약종·업종 코드 매핑       | common_code          | 상시        |  5   |     684 |
| 신재생에너지 현황   | 태양광·풍력 등 발전원별 설비      | renew_energy         | 2024      |  8   |     224 |

### 3.2 전처리

- **지역 코드 통일**: 지역명 텍스트(서울특별시, 전라북도 등)를 숫자 코드로 변환, `common_code` 테이블과 연계
- **집계행 제거**: API 원본의 전국 합계행(`totData`) 제거하여 이중 집계 방지
- **빈값 처리**: 빈 문자열(`""`)을 `NULL`로 변환
- **업종 코드 정비**: 한국표준산업분류(KSIC) 11차 기준으로 코드명 현행화
- **지역명 현행화**: 강원특별자치도, 전북특별자치도 반영

## 4. 주요 기능 구현

### 4.1 코드 변환기 (normalizer)

코드 변환기는 자연어 질문에서 지역명·업종명을 감지하여 `common_code` 테이블 서브쿼리 힌트를 자동 생성한다. 이를 통해 LLM이 코드를 하드코딩하는 오류(`biz_code = 'C'`)를 방지하고, 코드 체계가 변경되어도 자동으로 대응한다.

### 4.2 스키마 조합기 (semantic_builder) — 시맨틱레이어 3종

LLM이 올바른 SQL을 생성하려면 테이블 구조 외에 도메인 규칙을 알아야 한다. 스키마 조합기는 3개 레이어를 조합하여 LLM 프롬프트를 구성한다. 적용 수준은 `none`(DDL만) / `examples`(예시값) / `full`(전체 규칙) 3단계로 조절 가능하다.

| 레이어 | 내용 | 예시 |
|--------|------|------|
| 메타데이터 레이어 | 테이블 정의(DDL), 컬럼 예시값 | `gen_source` 예시: 태양광, 풍력, 소수력 |
| 의미규칙 레이어 | 단위, 집계 규칙, 사용 금지 패턴 | `unit_cost` 직접 평균 금지 → 가중평균 사용 |
| 조인관계 레이어 | 테이블 간 JOIN 가능 컬럼 정의 | `city_code`는 반드시 `metro_code`와 함께 사용 |

### 4.3 자기검증기 (verify, 선택)

생성된 SQL을 실행 전에 LLM으로 재점검하는 선택적 단계다. 질문의 조건이 SQL에 모두 반영됐는지, 조회 불가한 질문에 무리하게 SQL을 생성하지 않았는지 점검하여 누락은 수정하고 불가 질문은 거절한다.

- **조건 누락 보정**: 질문의 연도·지역 등 필터 누락을 탐지해 수정한다 (예: "2024년" 누락 시 `WHERE year='2024'` 추가).
- **조회 불가 거절**: 분류 기준상 존재하지 않는 지표(예: 업종별 계약전력)를 억지 JOIN으로 만들어내지 않고 거절한다.
- 정답 SQL은 수정하지 않아 회귀가 없으며, 평가에서 거절 정확도를 3종 모델 모두 100%로 끌어올렸다.

### 4.4 안전성 검사기 (safety)

LLM 생성 SQL 실행 전 4단계 검사를 수행한다.

1. **주석 제거**: 주석 내 금지 키워드 은닉 차단
2. **첫 토큰 검사**: `SELECT`/`WITH`/`EXPLAIN` 외 차단
3. **금지 키워드 검사**: `INSERT`, `UPDATE`, `DELETE`, `DROP` 등 차단
4. **테이블명 검사**: 스키마에 없는 테이블 참조 차단

`executor`의 PostgreSQL 읽기 전용 세션과 함께 이중 방어 구조를 형성한다.

### 4.5 SQL 실행기 (executor)

- psycopg2 `set_session(readonly=True)`로 읽기 전용 세션 연결, `statement_timeout` 5초 설정
- 결과 행 최대 100개 자동 제한
- 별도 스레드에서 실행, 5초 초과 시 타임아웃 강제 종료

## 5. 검증

### 5.1 평가 방법

생성 SQL의 정확도를 정답(gold) SQL과 비교하여 정량 측정하였다.

| 지표                           | 정의                        | 측정 방법                      |
| ---------------------------- | ------------------------- | -------------------------- |
| 정확도 (EX, Execution Accuracy) | 생성 SQL 실행 결과가 정답과 일치하는 비율 | gold SQL과 gen SQL 실행 결과 비교 |
| **실행 성공률**                   | 문법 오류·타임아웃 없이 실행 완료되는 비율  | 실행 오류·타임아웃 발생 여부 집계        |
| **거절 정확도**                   | 조회 불가 질문을 올바르게 거절하는 비율    | IMPOSSIBLE 시나리오 거절 여부 판정   |

※ 정확도(EX)는 완전 일치 외에 추가 컬럼 포함(superset) 및 핵심 수치만 반환(subset)도 정답으로 허용한다.

| 조건              | 정확도 (EX) 평균 | 실행 성공률 평균 | 거절 정확도 평균  |
| --------------- | ----------- | --------- | ---------- |
| ① 기본 (구조만)      | 57.6%       | 97.0%     | 0.0%       |
| ② 예시값 추가        | 57.6%       | 84.8%     | 33.3%      |
| ③ 도메인 규칙 전체     | 84.8%       | 97.0%     | 33.3%      |
| ④ 도메인 규칙 + 자기검증 | 87.9%       | 97.0%     | **100.0%** |

도메인 규칙 전체 주입(③)이 정확도를 57.6%→84.8%로 끌어올린 핵심 단계이며, 예시값만(②) 추가하면 효과가 없다. 자기검증(④)은 정확도를 87.9%로 더 높이고, 특히 거절 정확도를 0~33%대에서 100%로 끌어올린다.

# III. 연구 결과 및 도입 방안

## 1. 연구 결과

### 1.1 목표 대비 달성 현황

**SQL 자동 생성** — 자연어 질문을 SQL로 변환·실행하는 Text2SQL 6단계 파이프라인을 구축하였다.

**정확도 검증** — 자기검증 적용 시 gpt-oss-120b EX 100%(11/11), DeepSeek V3.2 90.9%(10/11), Qwen3-Coder-Next 72.7%(8/11)로 평가 대상 3종 모두 현장 활용 기준(EX ≥ 70%)을 초과 달성하였다.

**안정성 확보** — 안전성 검사기와 읽기 전용 실행의 이중 방어로 쓰기 구문을 원천 차단하였다.

**보안성 점검** — 오픈웨이트 모델(gpt-oss-120b)을 사내 폐쇄망에 자체 호스팅할 수 있음을 확인하였다.

### 1.2 개선 과제

**대화형 질의 고도화** — 현재 파이프라인은 질문 1건에 SQL 1건을 생성하는 단일 턴 방식이다. 다음 단계로 멀티턴 방식을 도입하여 앞선 질문의 결과를 이어받아 추가 질의를 할 수 있도록 고도화한다.

```
1문: "2024년 제조업 전력사용량 상위 5개 시도는?"  → [경기, 충남, 전남, 경북, 경남]
2문: "그 중 전년 대비 증가한 곳은?"  ← 앞 결과를 이어받아 조회
```

**개인·부서 맞춤 지식 연계** — 현재는 공통 DB 조회만 가능하다. 부서별 업무 문서·과거 보고서·자주 쓰는 질의 패턴을 RAG(검색 증강 생성)로 연계하여, 같은 질문이라도 부서 맥락에 맞는 답변을 제공할 수 있도록 한다.

**데이터 시각화 연계** — 조회 결과를 자동 차트화하는 등 시각화 서비스와 연계하여 데이터 활용도를 높인다.

**QnA 게시판 답변 지원 연계** — 사용자가 QnA 게시판에 올린 문의에 답변할 때, 문의 내용에 데이터 확인이 필요한 경우 Text2SQL로 실제 DB를 조회하여 그 결과를 답변 근거로 활용한다. 답변 담당자가 별도로 자료를 추출하거나 수치를 찾지 않아도, 문의에서 필요한 데이터를 자동 조회·반영하여 정확한 수치 기반 답변을 신속히 작성할 수 있도록 지원한다.

## 2. 기대 성과

**업무 효율 향상** — 도입 전에는 자료 추출을 한전KDN에 위탁하여 수일이 소요되었으나, 본 시스템은 직원이 자연어로 질문하면 SQL을 자동 생성·실행하여 즉시 결과를 확보한다. 연 13,582건('25년)의 위탁 자료추출을 셀프 처리로 전환함으로써 위탁 비용과 처리 시간을 절감한다.

**안정성 및 보안성** — 안전성 검사기와 읽기 전용 실행의 이중 방어로 데이터 변경을 원천 차단하며, 오픈웨이트 모델을 폐쇄망에 자체 호스팅하면 자료 데이터의 외부 유출 없이 운영할 수 있다.

**데이터 활용 역량 강화** — 위탁·소수 담당자에게 집중되어 있던 자료 추출 역량을 일선 직원으로 확산하여, 데이터 기반 의사결정 문화를 조직 전반에 정착시킨다.

## 3. 사내 도입 시 고려사항

**환경에 맞는 방법 선택과 지속적 개선** — NL2SQL의 성능 향상 기법은 단일 정답이 없으며, 데이터 규모·질문 다양성·사용자 전문성·정확도 요구 수준에 따라 효과적인 방법이 달라진다. 본 과제에서도 도메인 규칙 주입(시맨틱레이어)이 정확도에 가장 결정적이었고 자기검증이 거절 정확도를 끌어올렸으나, 예시값 주입은 오히려 성능을 떨어뜨리는 등 기법마다 효과가 엇갈렸다. 따라서 도입 환경의 특성을 먼저 진단하여 적합한 기법을 선택하고, Few-shot·캐싱·실행 후 검증 등 다양한 방법을 실제로 시험·비교하며 최적 조합을 찾아가는 지속적 개선 노력이 필요하다(기법별 특성은 [참고 2] 참조).

**담당자 확인 절차 유지** — 생성된 SQL과 결과는 담당자가 확인하는 절차를 유지한다. 시스템은 자료 추출을 보조하는 도구이며, 모든 실행은 읽기 전용으로만 수행되어 데이터 변경이 원천 차단된다.

**단계적 도입** — 광주·전남 사업소를 시범 대상으로 선정하여 실제 현장 질문 유형·오류 패턴·사용자 피드백을 수집한 후(2026년 하반기) 전국 사업소로 확대한다. 적용 범위도 영업배전 셀프 자료추출 기능을 우선 대체·보완하고, 도입 효과 검증 후 타 시스템으로 확장을 검토한다.

**폐쇄망 자체 호스팅** — 외부 API 의존성을 제거하기 위해 오픈웨이트 모델(gpt-oss-120b)을 사내 폐쇄망에 자체 호스팅한다. 이를 위해 대형 MoE 모델 구동에 필요한 GPU·VRAM 자원 산정이 선행되어야 한다.

## 참고 1. 시맨틱레이어 3종 상세

LLM에 주입되는 도메인 규칙을 세 레이어로 분리하여 관리하며, 평가 시 적용 수준(none/examples/full)을 조절하여 효과를 측정하였다.

| 레이어 | 주입 내용 | 대표 규칙 예시 |
|--------|-----------|----------------|
| 메타데이터 레이어 | 테이블 DDL, 컬럼별 예시값 | `month`는 '01'~'12' 두 자리 문자열 |
| 의미규칙 레이어 | 컬럼 의미·단위, 집계 규칙, 금지 패턴 | `area_capacity`는 MAX 사용 (SUM 시 중복 집계) / `unit_cost`는 가중평균 |
| 조인관계 레이어 | 테이블 간 JOIN 키, 복합키 규칙 | `city_code`는 `metro_code`와 복합키로만 사용 (단독 사용 시 카르테시안 곱) |

시맨틱레이어의 핵심 기여는 **모델 교체보다 도메인 규칙 주입이 정확도에 더 결정적**이라는 점을 정량으로 입증한 것이다(gpt-oss-120b 기준 미적용 54.5% → 도메인 규칙 전체 적용 81.8%, +27.3%p; 자기검증까지 적용 시 100%).

## 참고 2. NL2SQL 성능 향상 방법 정리

향후 고도화 및 사용 환경별 적용을 위한 참고 자료. 각 방법의 개선 대상·효과적인 환경·품질 영향을 정리하였다.

| 방법 | 설명 | 개선 대상 | 효과적인 환경 | 비효과/주의 | 품질 영향 | 난이도 |
|------|------|-----------|---------------|-------------|-----------|--------|
| 시맨틱레이어 (정적 주입) | 테이블·코드·집계 규칙을 프롬프트에 항상 고정 포함 | 도메인 무지 오류 | 규칙 복잡, 테이블 수십 개 | 스키마 단순 시 미미 | ◎ 정확도↑ | 낮음 |
| Few-shot 예시 (정적) | 정답 (질문,SQL) 쌍 몇 개를 프롬프트에 고정 | 특정 SQL 패턴 학습 | 반복 패턴·유형 적을 때 | 유형 다양 시 대표성 부족 | ○ 정확도↑ | 낮음 |
| Few-shot RAG (동적 예시) | 유사 질문의 정답 SQL을 검색해 주입 | 다양한 질문 대응 | 질문 다양 + 정답 SQL 축적 | 예시 풀 작으면 무효 | ◎ 정확도↑ | 중간 |
| 스키마 RAG (동적 테이블) | 질문 관련 테이블만 검색해 주입 | 컨텍스트 초과 회피 | 테이블 수백~수천 개 | 테이블 수십 개면 오검색 위험 | ○ 정확도↑ | 중간 |
| SQL 캐싱 (순수) | 생성된 SQL을 저장해 재사용 | 속도·비용·일관성 | 소수 질문 반복 | 첫 결과 오답 시 오답 고정 | △ 일관성만 | 낮음 |
| 사전 등록 (검증 SQL) | 사람이 검증한 SQL만 저장·재사용 | 정확도 보장 | 고정 대시보드·KPI | 신규 질문 대응 불가 | ◎ 정확도↑ | 낮음 |
| 모델 업그레이드 | 더 강력한 모델로 교체 | 추론·복합 JOIN | 약한 모델 한계 명확 | 이미 상위 모델 사용 중 | ○ 정확도↑ | 낮음 |
| Self-correction | 실행 에러 시 LLM에 재생성 요청 | 문법·스키마 오류 | 실행 오류가 주원인 | 의미 오류엔 무효 | ○ 정확도↑ | 중간 |
| Schema Linking | 관련 테이블·컬럼 먼저 식별 후 생성 | 잘못된 참조 | 테이블 多 + 컬럼명 모호 | 스키마 작으면 불필요 | ○ 정확도↑ | 중간 |
| 쿼리 분해 (CoT) | 복잡 질문을 단계로 쪼개 구성 | 복합 집계·중첩 | 다중 CTE·복합 질문 | 단순 조회엔 과함 | ○ 정확도↑ | 중간 |
| IMPOSSIBLE 거절 강화 | 불가·모호 질문에 추측 SQL 금지 | 잘못된 답 방지 | 비전문가·대외 서비스 | 거절 과다 시 사용성↓ | ◎ 오답↓ | 낮음 |
| 안전성 (읽기전용·인젝션 방어) | 위험 SQL 차단 | 보안 | 대외 공개 서비스 | 내부 전용은 우선순위↓ | — 보안 | 중간 |
| Fine-tuning | 도메인 데이터로 모델 재학습 | 도메인 특화 | 대량 데이터 + 고정 도메인 | 데이터 부족·도메인 변동 | ○ 정확도↑ | 높음 |

범례: ◎ 큰 영향 / ○ 유효 / △ 제한적 / — 해당없음

세 가지 핵심 구분:
- **품질 향상**: 시맨틱레이어, Few-shot, Self-correction, Schema Linking, 쿼리 분해, 거절 강화
- **성능(속도·비용)만**: 순수 캐싱 (품질과 무관, 동일 질문 일관성만 부여)
- **품질+성능 동시**: 사전 등록(검증 SQL)

### 사용 환경별 추천

| 사용 환경 | 특징 | 핵심 방법 |
|-----------|------|-----------|
| 고정 대시보드 | 소수 질문 반복 | 사전 등록(검증 SQL) + 캐싱 |
| 사내 분석가 도구 | 다양·전문가(검증 가능) | 시맨틱레이어 + Few-shot RAG + Self-correction |
| 일반 직원 셀프서비스 | 다양·비전문가(정확도 최우선) | 시맨틱레이어 + Few-shot RAG + Self-correction + 거절 강화 |
| 대외 공개 서비스 | 불특정 다수 | 안전성 + 시맨틱레이어 + Few-shot RAG + 캐싱 |
| 대규모 스키마 | 테이블 수백 개↑ | 스키마 RAG + Schema Linking |
| 실시간 운영 모니터링 | 저지연 필수 | SQL 캐싱·템플릿 + 경량 모델 |

> 본 과제(한전, 테이블 12개)는 **일반 직원 셀프서비스에 가깝고 스키마는 작은** 환경으로, RAG·Fine-tuning 없이 `시맨틱레이어 + Few-shot + 보수적 거절` 조합이 비용 대비 효과가 가장 크다. 스키마 RAG는 테이블이 수백 개 이상인 전사 통합 DW 단계에서 비로소 필요하다.
